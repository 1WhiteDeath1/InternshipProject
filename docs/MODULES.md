# Module Reference: Guests, Attendants, Members, Bookings, Billing, Clerk Desk, Attendance, Kitchen, Mess Billing

Technical reference for these 9 modules — what each contains, its workflow, and how it connects to the others. For general architecture (stack, auth, RBAC, audit logging) see `ARCHITECTURE.md` at the repo root. This doc is implementation-level (models, endpoints, FKs), not product-level — for the pitch/problem-statement framing see `docs/PROJECT_DOCUMENT.md`.

## Guests
**Models**: `Guest` (id, full_name, phone, id_type, id_number, unit_address) — pure identity dedup, no billing fields.
**Backend**: `backend/routers/guests.py` — `GET /guests/search?q=` (substring match on name/phone/id_number, capped 8, ordered by recency; gated on `guests:view` OR `bookings:view`, since Booking NCO needs this for check-in autocomplete but doesn't hold the standalone Customer Directory page). Neither Clerk nor Booking NCO hold `guests:view` - the directory page itself is unused by either role today.
**Connects to**: `Booking.guest_id` (nullable FK) — set by `_find_or_create_guest` in `bookings.py` on every booking creation (match by id_number, then phone; else create). Powers the check-in form's name/CNIC autocomplete. Guest has no FK back to Booking — one-directional.

## Attendants
**Models**: `Attendant` (id, name, shift, is_active, `on_duty`, `on_duty_since`).
**Backend**: `backend/routers/attendants.py`; `PUT /attendants/{id}/duty` for clock-in/out.
**Connects to**: `Room.attendant_id` (default/current housekeeper for a room) and `Booking.attendant_id` (snapshot of who was responsible during that specific stay — kept separate so reassigning a room later doesn't rewrite history). `on_duty` drives on-duty-first grouping in attendant pickers across the Bookings module.

## Members
**Models**: `Member` (id, service_number, full_name, rank, unit, `mess_category` [officers/jcos/ors], `client_category`, `is_womens_bloc`, `custom_discount_rate`, status).
**Backend**: `backend/routers/members.py` — list/search, `GET /members/{id}` (detail), `GET /members/{id}/residencies` (HRA booking history), status change.
**Frontend**: `Members.tsx` (roster + CRUD + Women's Bloc rate admin dialog), `MemberLedger.tsx` (`/members/:id` — Room Allocation + Dining tabs).
**Connects to**: `Booking.member_id` (set when a permanent resident occupies a room, `nature_of_duty="hra"`) → drives HRA rate lookup in `room_pricing.py` and monthly charge in Mess Billing. `MealAttendance.member_id` → drives man-days for Mess Billing and Kitchen production. `is_womens_bloc` branches which rank-rate table (`HraRankRate` vs `WomensBlocRankRate`) is used.

## Bookings
**Models**: `Room` (room_number, room_type, status, housekeeping_status, ac_count, attendant_id), `Booking` (room_id, guest_id, member_id, check_in/check_out, status [pending/confirmed/checked_in/checked_out/cancelled/no_show], `nature_of_duty` [visit/leave/official_duty/hra], client_category, stay_type, rank, da_multiplier, rate_breakdown JSON, `source` [walk_in/online] + `online_voucher_no`, `advance_payment_amount` + `advance_paid_at` — online bookings pay the room charge in full, in advance, outside SAM; mess still bills normally at checkout regardless of source; `kitchen_finalized_at/by` + `booking_finalized_at/by` — two independent, one-way checkout-readiness stamps, informational only, see below).
**Backend**: `backend/routers/bookings.py`; pricing engine in `backend/services/room_pricing.py` (`compute_booking_price`, `reprice_for_departure`, rate tables: `RoomRate`, `DutyRate`, `HraRankRate`, `WomensBlocRankRate`, `HraUtilityRate`, `TariffRate`). `GET /occupancy` returns today's/overdue departures for the Booking NCO dashboard, including both finalize stamps; `POST /bookings/{id}/finalize` (`bookings:edit`) stamps `booking_finalized_at` — Booking NCO confirming no more room/attendant ad-hoc charges are coming (they can log non-mess `BookingCharge` rows via `bookings:edit`, just not invoice) — posts a `LOW`-severity alert. Kitchen NCO's mirror lives in `kitchen.py` (`GET /kitchen/departures`, `POST /kitchen/departures/{id}/finalize`) — a narrow, `kitchen`-permission-gated view of the same departures (guest/room/unbilled mess+gas total only, not full Bookings access), stamping `kitchen_finalized_at` instead. Neither stamp blocks or triggers checkout; both surface in `GET /billing/bookings/{id}/running-balance` for the Clerk's `CheckoutSheet`.
**Workflow**: create/quote booking → room assigned → check-in (status→checked_in) → stay → check-out reprices actual nights stayed (folio practice) except HRA (bills monthly instead, never per-stay).
**Connects to**: Guest (identity), Member (HRA residents), Attendant (room service), Billing (checkout consumes Booking + its charges, and reads both finalize stamps for the checkout screen), Mess Billing (`_hra_charge_and_renew` reads `Booking.nature_of_duty=="hra"` rows monthly), Attendance (`MealAttendance.booking_id` for room guests' meals), Kitchen (its own departures/finalize endpoints stamp this same Booking).

## Billing
**Models**: `Invoice` (booking_id, `bill_type` [room/mess/combined], status, amounts), `InvoiceItem`, `BookingCharge` (booking_id, head, amount, `is_mess_charge` flag).
**Backend**: `backend/routers/billing.py` — `POST /bookings/{id}/instant-checkout` (atomic: frees room, reprices, gathers unbilled room+mess items via `_gather_unbilled_items`, issues invoice(s) — **no draft/lock state, checkout=settling the bill everywhere**, no standalone check-out-only endpoint exists), `GET /bookings/{id}/running-balance` (live preview, same gather logic so preview==invoice), `GET /bookings/{id}/master-invoice` (merges room+mess invoices into one printable doc), `GET /invoices/{id}/print-data`. **Room charges are itemized, not one lump sum**: `_gather_unbilled_items` reads `Booking.rate_breakdown`'s `components` dict (from `compute_booking_price`, see Bookings/`room_pricing.py`) and emits one `InvoiceItemCreate` per component (rent/electricity/generator/gas/internet, or the tariff/duty/HRA equivalent — see `ROOM_COMPONENT_LABELS`), each individually correctable via `instant-checkout`'s `room_component_overrides: Dict[str, float]` (keyed the same as `components`) + a shared `room_override_reason`; a legacy booking with no component snapshot falls back to one overridable `"base"` line. Every `InvoiceItemCreate` (preview and real) carries `component_key` (computed, correctable) or `charge_id` (an ad-hoc `BookingCharge`, removable) or neither (a fixed structural line — Extra Mattress/Late Checkout Fee) — `_running_balance_payload` surfaces these on each room/mess item so the frontend can render the right control per row without re-parsing the description string. Reporting/export, all gated on plain `billing:view` (not the Manager-only `reports` module, so Clerk reaches these on the permission it already holds): `GET /reports/summary?period=month|year&date=` (returns `room`/`mess` each as `{income, cost, margin}` — **`room.cost`/`room.margin` are always `None`**, since nothing in this system tracks a housekeeping/utility/maintenance cost for a room; `mess.cost` is real — self-purchase stock spend (`StockBatch`, logged via Daily Stock Intake/Smart Intake — the mess buys and restocks itself, there's no PO workflow) + logged WasteLog cost, both entirely kitchen/mess stock — plus discounts, voids, overdue, cash-in by payment method), `GET /stock-summary` (total stock value + top items by value + low-stock count — deliberately narrow, does not grant `inventory:view`), `GET /export/invoices` and `GET /export/payments` (Excel via openpyxl, optional `start`/`end` date bounds). Frontend for the reporting/export slice is `src/pages/BillingReports.tsx` (route `/billing-reports`, nav label "Income & Cost") — a standalone top-level page, not nested under Clerk Desk, reachable by anyone with `billing:view` (Clerk only, today).
**Connects to**: Bookings (1 stay → up to 2 Invoices, room+mess, generated together or deferred separately), Kitchen/Attendance (unbilled `MealAttendance`/`KitchenOrder` rows feed the mess side of a guest's bill), Inventory (`StockBatch`/`WasteLog` feed `mess.cost` on the Income & Cost report), Clerk Desk (the UI that drives checkout/settlement itself).

**Manager discount/category authority**: no discount action lives on the Clerk Desk bill dialog (`BillPrintView`) itself — a guest who's still checked in has no invoice yet (this app bills at checkout, not before), so a discount there is applied directly to the *booking* instead (`PUT /bookings/{id}/discount`, threaded through the pricing engine alongside `client_category` so it survives every re-price) via the dedicated **Guest Discounts** page (`src/pages/GuestDiscounts.tsx`, `bookings:approve`). HRA/mess members get a standing discount the same way via **Member Discounts** (`src/pages/MemberDiscounts.tsx`), reusing `Member.custom_discount_rate` which `mess_billing.generate_bills` already applies every period. `BillPrintView`'s Room/Mess/Combined tabs are always shown once a `bookingId` is known (a missing side renders as a Rs 0 bill rather than hiding the tab), and the Combined view lays its items out over the same fixed paper-form heads `DraftBill` uses (room heads + mess heads together) so a zero line shows "—" instead of disappearing. The bill-correction workflow (`InvoiceEditRequest`) can now also add a charge under a head that's currently zero/uncharged, not just correct an existing line (`invoice_item_id` is nullable; `POST /billing/invoices/{id}/edit-request`).

## Clerk Desk
**Not a data model** — a worklist view over Billing + Bookings + Mess Billing.
**Backend**: `GET /billing/desk` — checked-in non-HRA bookings + `unsettled_invoices` (live invoices with money owing). Deliberately does NOT surface a "checked out but still unbilled" state — checkout (`instant-checkout`) always bills everything owed in one shot (walk-ins pay room+mess together on the spot; online guests prepaid the room in advance, so only mess is due at checkout), so there's no legitimate gap to worklist there; a booking only reappears after checkout via `unsettled_invoices` if its bill was generated but not fully paid. `GET /billing/mess-only-desk` — walk-in (no room booking) guests with unbilled meals. Member billing reuses the `/mess-billing/*` endpoints (see Mess Billing below) — Clerk Desk adds no endpoints of its own for that side.
**Frontend**: `src/pages/clerk-desk/` — `ClerkDeskLayout.tsx` (shared data fetch for the desk/mess-only/member-bill feeds + the tab strip) wraps four tabs, no dashboard/overview tab (the Clerk's headline numbers live on the main `/dashboard` page instead, see below): `LiveGuests.tsx` (checked-in, folio still accruing, the only place `CheckoutSheet.tsx` is opened from), `Checkout.tsx` (settle queue over already-generated `unsettled_invoices` only → `BillPrintView`/`MasterInvoiceView` from `BillPrint.tsx`), `MessOnly.tsx` (walk-in guests, generates a mess-only invoice), `Members.tsx` (the monthly member mess-bill workflow, merged in from the old standalone Mess Billing page — card grid grouped Newly Generated/Issued/Paid, issue/mark-paid/discount/print actions, a read-only guest-meal-charges panel). The month/year income-vs-cost report (formerly a fifth tab here) now lives at its own route, `/billing-reports` (`src/pages/BillingReports.tsx`) — see Billing above; it isn't part of Clerk Desk at all, so it fetches independently rather than through `ClerkDeskLayout`'s shared feed. Payment collection for guest stays happens entirely here; the Billing page is history/search only. Clerk holds full `mess_billing` access (view/create/edit/approve) but Members.tsx still intentionally excludes bill *generation* and guest-charge *logging* by design (UI simplicity, not a permission gap) - those stay on the standalone Mess Billing page (see below); Members.tsx picks up from the drafts it produces. Room/mess ad-hoc charges (Dhobi, Breakage, Extra Messing...) are logged via the global "+ Log Charge" quick action (`QuickChargeModal`, reachable from the Billing page) rather than from Clerk Desk itself.
**Dashboard**: the Clerk's own `/dashboard` view (`src/pages/Dashboard.tsx`, `isClerk` branch) is a deliberately compact, single-screen "financial pulse" — four large hero tiles only (today's/month's collections, outstanding across room+mess+member billing, count of bills pending action), each linking into Clerk Desk for the actual detail. No charts, lists, or breakdowns on the face.
**Connects to**: Bookings (source of truth for who to bill), Billing (the actual checkout action), Guests (display names), Mess Billing (Members tab operates the same `MessBill` rows the standalone Mess Billing page generates).

## Attendance
**Models**: `MealAttendance` (member_id **or** booking_id — exactly one, date, meal_type, `status` [booked/attended/cancelled/excluded/no_show], menu_item_id), `MemberLeave`.
**Backend**: `backend/routers/attendance.py` — book/mark/roster endpoints, `GET /attendance/lookup` (omnibar search), `POST /attendance/serve` (idempotent create-or-confirm), `POST /attendance/no-show-sweep` (manual — no scheduler in this app).
**Workflow**: a person books/is served a meal for a date+meal_type → status flows booked→attended, or booked→no_show if never served past the meal window+grace.
**Frontend**: single page, `src/pages/Attendance.tsx` (nav item under "Kitchen & Stock") — meal-type cards (breakfast/lunch/hitea/dinner, cutoff/lock badges) drive an omnibar (`GET /attendance/lookup` + `POST /attendance/serve|attendance`, for members/checked-in guests/standalone walk-ins) and a Dining/Non-Dining/Room-Guests roster of `Switch` toggles backed by `GET/POST /attendance/matrix` (each toggle is an instant single-entry POST, not a batched save). There used to be a second, separate roster UI as a Kitchen tab — it was folded into this page; Kitchen's per-row "Special Order" shortcut now deep-links here→there via `navigate('/kitchen', {state: {openAlaCarte, presetConsumerKind, presetConsumerId}})`, consumed in `Kitchen.tsx`'s location-state effect.
**Connects to**: Members and Bookings (the two possible owners of a row), Kitchen (`_aggregate_suggestions` groups booked/attended rows by menu item to generate production orders; à la carte dialog is the Special Order deep-link target), Mess Billing (`get_man_days` counts ATTENDED+NO_SHOW rows for the per-head rate), Billing (guest-linked rows in `booked/attended/no_show` bill at guest checkout).

## Kitchen
**Models**: `MenuItem` (name, meal_type, day_of_week, editable estimated `price` — no ingredient/costing data, the "automatic" default a dish's food charge falls back to when no override is set), `MenuItemEditRequest` (Kitchen NCO proposes an add/edit; Manager approves/rejects before it goes live — same shape as `InvoiceEditRequest`), `GasChargeRate`/`GasChargeRateHistory` (a single Kitchen-NCO-set percentage applied to a dish's *effective* price as the fallback gas estimate when no per-dish amount is set — no approval gate, every change logged for the Manager's trend graph), `MealGasCharge` (superseded — the old flat per-date+meal gas amount; the model/table is left in the schema unused, per this app's no-drop migration policy, but nothing reads/writes it anymore), `KitchenOrder` (routine + à la carte, status pending→prepared/cooking→served, `is_ala_carte`, member_id/booking_id for à la carte consumer, `gas_amount` + `price_override` — a per-head gas charge and a food-price override the Kitchen NCO sets together, once per routine batch order, via one dialog on its Production-tab row; only meaningful when `is_ala_carte=False` and `meal_date`/`meal_type` are set, i.e. generated via "Generate from bookings" or found/created on the fly by `PUT /kitchen/dish-pricing`, never a dateless manual order).
**Backend**: `backend/routers/kitchen.py` — `GET /suggested-orders` (from Attendance), `POST /orders/generate` (promotes suggestions to KitchenOrders), prepare/cook/serve/à-la-carte lifecycle (no inventory deduction — stock is reconciled manually via Inventory's Cycle Counts instead); `PUT /kitchen/dish-pricing` (`mess_rates:edit`, body `{date, meal_type, menu_item_id, price_override, gas_amount}`) finds or creates the matching routine `KitchenOrder` for that triple and sets both fields together — the single endpoint behind both the Production tab's pricing icon and the per-meal breakdown table below; `GET/POST /menu` + `PUT /menu/{id}` (propose add/edit) + `GET /menu/edit-requests` + `POST /menu/edit-requests/{id}/approve|reject` (the Menu approval flow); `GET/PUT /gas-rate` + `GET /gas-rate/history` (mess-wide % fallback); `GET /mess-charges-overview` (every active Member + checked-in Guest's unbilled mess total + live gas preview, plus per-guest `is_departing`/`kitchen_finalized_by_name`/`booking_finalized_by_name` context, see `backend/services/mess_charge_calc.py`) + `GET /order-history` (full billed+unbilled order history for one member/booking/guest, now also carrying `menu_item_id`/`price_is_override`/`gas_amount` per row so it doubles as the editable breakdown's data source); `GET /departures` + `POST /departures/{booking_id}/finalize` (Kitchen NCO's checkout-readiness view/sign-off — see Bookings above).
**Pricing mechanics**: `mess_charge_calc._dish_pricing_order(db, meal_date, meal_type, menu_item_id)` looks up the matching non-cancelled routine `KitchenOrder` for that exact date+meal+dish (no FK — matched the same way production-order generation already matches attendance to orders); `_effective_dish_price` reads its `price_override` (falling back to `MenuItem.price`). `compute_unbilled_mess_total`'s attendance-row pricing, `compute_unbilled_gas_total` (guest/walk-in, at checkout), and `get_member_gas_total` (member, monthly) all resolve through these — gas falls back to `GasChargeRate`'s percentage of the *effective* (possibly overridden) price when no order-level gas amount is set. Editing either field from ANY consumer's view (the Production tab icon, or a guest's breakdown table below) changes the shared `KitchenOrder` row, so it applies to everyone who ate that exact dish, not just one person. This is a real behavior change from the old model: **members now accrue a genuine per-attendance gas charge** (`MessBill.gas_amount`, computed in `generate_bills`, individually correctable via `correct_mess_bill_field` like `base_menu_amount`/`stay_amount`) — previously member routine dining had zero gas component, only their à la carte total got the percentage estimate. À la carte orders are unaffected by either field (see the model docstring) — always priced at the plain menu price × quantity.
**Frontend breakdown**: `src/components/DishBreakdownDialog.tsx`, opened from a **guest** row's "Breakdown" action in Kitchen's Mess Charges Overview (member rows only get "Log Charge" — a member's dining is billed monthly in aggregate, not per meal, so there's nothing per-dish to correct for them there; their full meal history instead lives read-only in `MemberLedger.tsx`'s "Dining & Mess Account" tab, sourced from the same `GET /order-history`). Each row is one meal/order with inline Food + Gas inputs (à la carte rows are display-only); saving a row calls `PUT /kitchen/dish-pricing`. If the guest is also in the Departures list, the dialog shows a "checking out" banner with the same Finalize & Notify Clerk action as the Departures tab.
**Connects to**: Attendance (production input; attendance rows are also what per-dish gas charges are matched against), Billing (`mess_charge_calc.compute_unbilled_mess_total`/`compute_unbilled_gas_total` consolidate a guest's/walk-in's routine meals + à la carte into one "Extra Messing" + one "Sui Gas Charges on Messing" invoice line, both overridable at checkout; see `backend/routers/billing.py:_gather_unbilled_items`/`_gather_walkin_items`), Mess Billing (`MenuItem.price` still prices member `MessBill.ala_carte_amount` directly; `MessBill.gas_amount` is the new per-dish-derived member gas total), Bookings (departures/finalize share the same `Booking` rows and stamps), Approvals page (Manager decides pending `MenuItemEditRequest`s alongside PO/bill-correction approvals), Reports (Gas charge rate trend chart), Clerk Desk (Order History buttons on Checkout/MessOnly/Members tabs; `CheckoutSheet` shows both departments' finalize status).

## Mess Billing
**Models**: `MessBill` (member_id, month, year, man_days, per_head_rate, `base_menu_amount`, `stay_amount` [room/HRA side], `extra_meals_amount`, `ala_carte_amount`, `gas_amount` [per-dish-derived Sui Gas total for the period's routine dining, see Kitchen above], discount fields, total_amount, status [draft/issued/paid]), `GuestMealCharge` (member-sponsored guest meals — unrelated to the per-dish gas mechanism; no `menu_item_id`, still priced via the mess-wide `GasChargeRate` percentage only).
**Backend**: `backend/routers/mess_billing.py` — `POST /generate?month=&year=` (`mess_billing:create` — one MessBill row per active member per period; `stay_amount` = non-HRA booking totals + `_hra_charge_and_renew` HRA/Women's-Bloc figure; dining = attendance-derived per-head rate + extras + à la carte + `get_member_gas_total`), `POST /issue-all` / `POST /bills/{id}/issue` / `POST /bills/{id}/apply-discount` (`mess_billing:approve`, recompute includes `gas_amount`), `POST /bills/{id}/mark-paid` (`mess_billing:edit`), `POST /guest-charges` (`mess_billing:create`), `PUT /bills/{id}/correct-field` (now also accepts `gas_amount`, alongside `base_menu_amount`/`stay_amount`), `GET /room-lease-dispatch` (Pipeline A — aggregate stay_amount across members, HRA vs Women's Bloc subtotal), `GET /bills/{id}/diet-invoice` (Pipeline B — dining-only, excludes stay_amount, includes gas_amount). `GET /bills` also returns each bill's member "type" (`member_rank`, `member_mess_category`, `member_is_womens_bloc`, `member_service_number`), joined in for display — Clerk Desk's Members tab is the main consumer.
**Frontend**: two entry points for the Clerk over the same data - `src/pages/MessBilling.tsx` (generate the period's bills, log sponsored guest meal charges) and Clerk Desk's `Members.tsx` (issue/collect/discount/print what got generated); both are reachable since Clerk holds full `mess_billing` access. Booking NCO holds neither `billing` nor `mess_billing` at all - Clerk owns money end-to-end.
**Connects to**: Members (billed entity), Bookings (HRA + non-HRA booking totals), Attendance (man-days and, per attended row, the per-dish gas match), Kitchen (à la carte cost; `KitchenOrder.gas_amount` is now the primary source of `MessBill.gas_amount`, percentage fallback only when unset).

## Two end-to-end pipelines

**Guest stay** (transient, per-visit): Guest → Booking (room, non-HRA) → check-in → Attendance rows (meals) → Kitchen produces from them + BookingCharges accrue → check-out via Clerk Desk → Billing instant-checkout gathers everything unbilled → Invoice(s) issued. Settles once, at checkout.

**Member residency** (recurring, monthly): Member → Booking (`nature_of_duty="hra"`, no per-stay bill) + Attendance rows (meals) → Kitchen produces from them → month-end the Clerk runs `POST /mess-billing/generate` (standalone Mess Billing page) which aggregates HRA/Women's-Bloc room charge (`stay_amount`) + dining (attendance × per-head rate + extras + à la carte) into one draft `MessBill` per member → picked up in Clerk Desk's Members tab to issue/collect/discount → optionally split for output only via Room-Lease Dispatch (org) / Diet Invoice (individual). Never touches guest `Invoice`.
