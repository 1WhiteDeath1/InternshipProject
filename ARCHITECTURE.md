# Architecture

Orientation for anyone working on this codebase: the stack, how the two halves fit together, and the conventions to follow when adding to it.

## Project Overview

SAM (branded in-app as EME MESS) — a production-grade, offline/on-premise hotel and mess (canteen) management system for an EME Officers Mess. FastAPI backend (`backend/`) + React/TypeScript/Vite frontend (`src/`), backed by SQLite. Designed to run entirely on a local network with no internet dependency. Packaged as a Windows installer via `packaging/` (see `packaging/build.ps1`) — there is no standalone INSTALL.md; the installer is the deployment path (see Notes below).

For implementation-level detail on the guest/member/booking/billing cluster (models, endpoints, FKs, the two end-to-end billing pipelines), read **[docs/MODULES.md](docs/MODULES.md) first** — it's a maintained reference, more current and more precise than trying to re-derive that cluster from source. Update it (not just memory) when those modules change shape.

Before adding a model, schema, endpoint, or migration — or working with multiple contributors/agents in this repo at once — read **[docs/MODULE_STRUCTURE.md](docs/MODULE_STRUCTURE.md) first**. It defines the domain-package convention (`models/`, `schemas/`, `migrations/` are each split one file per domain, mirroring `routers/`) that keeps parallel work merge-conflict-free, and the rule for extending an existing domain vs. creating a new one.

## Commands

### Frontend (run from repo root)
- `npm run dev` — Vite dev server on port 3000; proxies `/api`, `/docs`, `/openapi.json`, and `/uploads` to the backend on port 8000 (see vite.config.ts)
- `npm run build` — `tsc -b && vite build`, outputs to `dist/`
- `npm run lint` — `eslint .`
- `npm run preview` — preview the production build

### Backend (run from repo root, NOT from inside `backend/` — imports use the `backend.` package prefix)
- Windows: `start.bat` → `python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --reload`
- Linux: `./start.sh` → `python3 -m uvicorn backend.main:app --host 0.0.0.0 --port 8000`
- Dependencies: `pip install -r requirements.txt` (unpinned)
  (the last three - `rapidocr-onnxruntime`, `opencv-python-headless`, `rapidfuzz` - power the Smart Intake receipt-OCR feature in Inventory/Procurement — see `backend/services/receipt_ocr.py`)
- Seed demo data: `python backend/seed_demo.py` — creates one demo user per RBAC role (`manager`, `deputy`, `clerk`, `kitchen`, `booking`, `security`; password `123456` for all — offline demo data only, deliberately trivial) plus sample inventory/rooms/bookings/vendors
- No automated test suite exists for either the backend or frontend currently.

## Architecture

- Single project root containing two colocated codebases — a Vite/React app (`src/`) and a FastAPI package (`backend/`) — not a monorepo with workspaces.
- **Serving model**: In dev, Vite (port 3000) proxies API calls to FastAPI (port 8000). In production, `npm run build` outputs `dist/`, and `backend/main.py` mounts `dist/assets` as static files and serves `dist/index.html` for any non-API path (SPA fallback), so the whole app runs from one FastAPI process/port. The SPA catch-all is registered last in `main.py` specifically so it can't shadow real `/api/*` routes.
- **Data layer**: SQLite at `backend/hotel_mess.db`. Tables are created via `Base.metadata.create_all()` in `backend/main.py` on startup — despite `alembic` being in the install list, no migrations are actually wired up. `Base.metadata.create_all()` only adds *new* tables, it never alters existing ones, so every additive schema change (new column, new table added to an existing feature) also needs a one-off idempotent patch function in `backend/migrations/<domain>.py` (one file per domain, mirroring `models`/`schemas`/`routers` — see `docs/MODULE_STRUCTURE.md`), appended to that domain's `MIGRATIONS` list. `backend/migrations/__init__.py`'s `run_startup_migrations(engine)` runs every domain's list right after `create_all()` on every startup. When you add/change a column on an existing model, add the matching migration function to your model's domain file (follow the existing `_migrate_*` naming pattern) — don't rely on `create_all()` alone or existing DBs won't pick up the change.
- **Config**: `backend/config.py` centralizes filesystem paths (`DB_PATH`, `LOGS_DIR`, `BACKUP_DIR`, `BRANDING_FILE`, `UPLOADS_DIR`) and a pydantic-settings `Settings` object (JWT secret/expiry, login lockout policy, backup retention) loaded from an optional `.env` file.
- **Auth & permissions** (`backend/auth.py`): JWT bearer tokens. RBAC model is `Role` → `RolePermission` (module + action pairs, e.g. `inventory`/`create`) → `User`. `role.is_supervisor` is a total bypass of `check_permission()` — it can't be scoped, so none of the 6 seeded roles use it (see `_ROLE_PERMISSIONS` in `backend/migrations/access.py`); it exists only for a hypothetical break-glass account via `Depends(require_supervisor)`. Use `Depends(get_current_user)` for authentication and `check_permission(user, module, action)` / the `PermissionChecker` dependency for authorization on every endpoint, including reads that carry PII or financial data — only low-sensitivity reference-data GETs are left ungated.
- **Audit logging** (`backend/audit.py`): `log_audit(...)` writes immutable `AuditLog` rows with JSON before/after snapshots (via `serialize_model`). Every router calls this after create/update/delete/approve actions — follow this pattern for any new mutating endpoint.
- **Routers** (`backend/routers/*.py`): one file per business domain, each mounted in `backend/main.py` under `/api/<domain>`: `auth, users, roles, inventory, procurement, bookings, billing, security, reports, audit, alerts, settings, features, import_export, backup, branding, members, attendance, mess_billing, kitchen, guests, attendants, tariffs, womens_bloc_rates, events, directives, rate_card`. All follow the same shape: `Depends(get_db)` for a scoped session, `Depends(get_current_user)`, a `check_permission` guard before mutating, and a `log_audit` call after.
  - **List endpoints cap `page_size` at 100.** Never treat a single page as the full set — a `page_size=100` fetch with no further paging silently truncates once a list crosses 100 rows. When a screen needs a total or an aggregate (a count, a sum, "everything for this date range"), add a dedicated aggregate endpoint that computes it server-side (e.g. a `GROUP BY`) rather than paging through and summing client-side.
- **Services** (`backend/services/*.py`): cross-router business logic that doesn't belong to a single endpoint file — `room_pricing.py` (booking price computation/reprice, the rate-table engine), `mess_billing_calc.py`, `mess_charge_calc.py` (Extra Messing/Gas charge computation from actual orders), `receipt_ocr.py` (Smart Intake OCR parsing), `anomaly_engine.py` (statistical anomaly detection — z-score on procurement spend, Benford's Law on stock-intake unit costs), `sms.py`. Routers call into these rather than embedding pricing/costing logic inline. There is no recipe/ingredient costing or per-ingredient kitchen stock deduction — a kitchen order's menu item carries an estimated price, not a costed recipe, and stock is reconciled manually via Cycle Counts.
- **Domain model** (`backend/models/`, one file per domain — `access`, `system`, `audit`, `alerts`, `inventory`, `kitchen`, `procurement`, `rooms`, `rates`, `guests`, `bookings`, `billing`, `security`, `members`, `attendance`, `mess_billing`, `events`, plus shared `enums.py`; `models/__init__.py` re-exports everything so `from backend.models import X` is unaffected by which file `X` lives in — see `docs/MODULE_STRUCTURE.md`) groups into: Users/Roles/Permissions; Inventory (categories, items, stock batches, stock movements, waste logs, cycle counts); Recipes/Kitchen (recipes, ingredients drawn from inventory, kitchen orders, menu prices); Procurement (vendors, purchase orders, three-way match against deliveries); Bookings (rooms, bookings, guests, attendants, guest movements, rate tables — `RoomRate`/`DutyRate`/`HraRankRate`/`WomensBlocRankRate`/`HraUtilityRate`/`TariffRate`); Members & Attendance (members, meal attendance, leave); Billing & Mess Billing (invoices/invoice items/payments, booking charges, mess bills, guest meal charges); Events (`Event`/`EventMenuItem` — hall/function bookings for a group, a free-text priced menu, a kitchen prep lifecycle, and a billing-type flag; distinct from the guest-Room `Booking` flow, though a completed event generates a real guest-linked `Invoice` with `bill_type='event'`); Security (security logs, incident reports); plus cross-cutting `AuditLog`, `Alert`, `FeatureFlag`, `SystemSetting`, `SmsMessage`. `backend/schemas/` mirrors the same per-domain split for Pydantic request/response models.
- **Feature flags**: `FeatureFlag` model + `/api/features` + `src/contexts/FeaturesContext.tsx` allow toggling modules per department at runtime.
- **Frontend routing** (`src/App.tsx`): flat `react-router-dom` v7 route table. `SplashScreen` and `Login` sit outside the authenticated shell; all other pages (Dashboard, StockManagement, Bookings, Billing, ClerkDesk, BillingReports, Guests, Attendants, Tariffs, Members, MemberLedger, Attendance, MessBilling, Kitchen, Security, Users, Roles, AuditLog, Alerts, Directives, Approvals, Reports, Settings, ImportExport, Events, GuestDiscounts, MemberDiscounts) render inside the shared `Layout` (`src/components/Layout.tsx`). There is no standalone Procurement or Inventory page — self-purchase stock intake and vendor management live inside `StockManagement.tsx`; there is no purchase-order workflow (the mess buys and restocks itself, see `backend/routers/procurement.py`'s docstring).
- **Frontend state**: `AuthContext` (JWT in `localStorage`), `ThemeContext`, `FeaturesContext` wrap the route tree in `App.tsx`. `src/lib/api.ts` is the single axios instance to use for all API calls — it attaches the Bearer token and force-redirects to `/login` on a 401 for an already-authenticated session.
- **UI kit**: shadcn/ui ("new-york" style, see `components.json`), pre-generated components live in `src/components/ui/`. Reuse these rather than hand-rolling primitives; add new ones through shadcn using the existing config.
- **Path alias**: `@/*` → `src/*` (see `vite.config.ts` and `tsconfig.app.json`).

## Notes
- No `.env` file is present; `SECRET_KEY` and other settings fall back to defaults in `backend/config.py` — for any real (non-demo) deployment these must be overridden via `.env`.
- `README.md` describes generic Vite/shadcn scaffolding and is stale relative to the actual application. `projectDirectory.md` is also stale (missing routers/pages/services added since) — don't treat it as authoritative for current file layout.
- **Deployment is via the packaged Windows installer, not a source checkout.** `packaging/build.ps1` runs `npm run build` → PyInstaller (`packaging/EME-MESS.spec`, entry point `packaging/launcher.py`) → Inno Setup (`packaging/installer.iss`), producing `packaging/output/EME-MESS-Setup-<version>.exe`. Bump the version in both `package.json` and `packaging/installer.iss` (`MyAppVersion`) before each build — nothing auto-syncs them. `launcher.py` binds the bundled server to `127.0.0.1` only (single-machine, not LAN-reachable) — it's built for one client to test on their own PC, not the multi-device local-network deployment described above; re-point `HOST` in `launcher.py` (and open the firewall port) before shipping a build meant to serve multiple client devices on the network.
- If you add a new backend dependency, add it to `requirements.txt` (repo root) — the PyInstaller build picks it up from the venv it's run in, nothing else needs updating.
- `backend/venv/` is a local Python virtualenv checked into this folder — not source code, ignore its contents when reading/searching.
- `backend/dev_server.py` is a dev-only entrypoint used by the preview harness: it picks a free port via the `PORT` env var (instead of the fixed 8000 in `start.bat`/`start.sh`) and writes it to a temp file so `vite.config.ts`'s proxy (a separately-launched process) can discover it. Not used in production.
